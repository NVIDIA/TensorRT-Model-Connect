# LayoutLM document question answering (`layoutlm`)

Answers a question about a document image with an extractive
`LayoutLMForQuestionAnswering` checkpoint, the way transformers'
`document-question-answering` pipeline does: Tesseract OCR reads the words and
their boxes, the encoder scores answer starts and ends over the words, and the
best span is returned as text.

| | |
| --- | --- |
| Task | `images_text_to_text`: one user message with one document image and one question |
| Output | `text`: the answer words joined by one space, empty when no span qualifies; `token_ids`: the input token ids of the answer span |
| Checkpoints | `LayoutLMForQuestionAnswering` with a RoBERTa byte-level BPE tokenizer, for example `impira/layoutlm-document-qa` |
| Precision | `fp32` (the checkpoint's own) or `fp16`; the fp16 engine keeps LayerNorm, softmax and GEMM accumulation in float32 |
| Runtime config | none: the pipeline's defaults are fixed (top 1 answer, at most 15 tokens, no impossible-answer option, English OCR, automatic page segmentation) |

## Requirements

The runtime loads the user-installed Tesseract OCR library (`libtesseract.so.5`,
Apache-2.0) with its English language data on first use; the family neither
links nor ships it, and a missing library is reported as an error. The E2E
reference runs the `tesseract` command of the same installation. On Ubuntu:

```bash
apt-get install tesseract-ocr tesseract-ocr-eng
```

Tesseract 5 is required: releases that ship Tesseract 4 (`libtesseract.so.4`,
for example Ubuntu 22.04) fail with the missing-library error. `TESSDATA_PREFIX`
selects another language-data directory. Answers depend on the Tesseract version
and language data, as the reference pipeline's do. Validated: Tesseract 5.3.4
with English data 4.1.0 (Ubuntu 24.04) on x86_64.

Loading the library also loads its own dependencies into the process. In
Debian and Ubuntu builds these include Leptonica, libtiff and, through libtiff,
JBIG-KIT (GPL-2.0-or-later); review the licenses of the Tesseract build you
install before redistributing it with this runtime.

## Build and run

```bash
python -m tensorrt_model_connect build impira/layoutlm-document-qa \
  --output layoutlm.bundle --family layoutlm --task images_text_to_text --precision fp32
trtmc run layoutlm.bundle --image invoice.png --prompt "What is the invoice number?"
```

`--max-sequence-length` sets the window, by default the tokenizer's
`model_max_length` (512 for `impira/layoutlm-document-qa`); the stride between
windows is `min(window // 2, 256)`, as in the pipeline.

## Behavior and limits

- Long documents are split into overlapping windows; the best-scoring span over
  all windows wins, the earlier window on a tie.
- Images may be gray, RGB or RGBA, as uint8 or as float32 in [0, 1]; alpha is
  dropped. The command line decodes image files with stb_image, which does not
  apply EXIF orientation and decodes JPEG slightly differently from PIL, so a
  rotated photo or a JPEG can read differently from the pipeline. Upright
  lossless images give the reference's pixels.
- Refused when building: tokenizers other than byte-level BPE with the RoBERTa
  pair framing (for example WordPiece LayoutLM checkpoints), relative position
  embeddings, activations other than the exact GELU, left truncation, and
  `cls_token` / `sep_token` settings that differ from the pair framing.
- Not exposed: the pipeline's answer score and word indices, more than one
  answer, impossible answers and caller-supplied word boxes.

## Validation

`tests/test_e2e.py` builds the pinned checkpoint and, per question, requires
the native answer text and answer token ids to equal those of transformers'
pipeline (pytesseract running the `tesseract` command of the same Tesseract version), the engine logits
to stay within a tolerance measured against deliberately broken engines, and the
public C and C++ SDK consumers to return the command line's answer. The C++
checker `tests/cpp/test_document_qa.cpp` runs without a GPU on goldens recorded
from the reference libraries (`tests/data/generate_goldens.py`): word token
ids, overflowing windows, question splitting, Tesseract TSV reading, span
decoding and image conversion. The documents are generated by
`tests/data/generate.py`.
