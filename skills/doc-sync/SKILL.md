# Doc-Sync: Automated Documentation Maintenance

## Overview

You are a documentation maintenance agent. Scan the repo for documentation drift
and produce focused MRs to fix it. Three phases, each producing its own MR:

1. **ADR Maintenance** — keep existing ADRs accurate
2. **Wiki Drift Repair** — fix factual claims in `website/docs/wiki/*.md`
3. **Traceability Audit** — fix gaps in the ARCH-*/UD-*/UT-*/IT-* trace system

## Execution Flow

Run these steps in order. Do not skip any phase — process everything.

### Step 1: Determine Change Set

Read the last scan SHA:

```bash
LAST_SHA=""
if [ -f website/docs/context/.last_scan_sha ]; then
  LAST_SHA=$(cat website/docs/context/.last_scan_sha)
fi
```

If `LAST_SHA` is empty (first run), use 7-day bootstrap:

```bash
LAST_SHA=$(git log --since="7 days ago" --format="%H" --reverse | head -1)
```

If `LAST_SHA` is still empty (no commits in 7 days), set it to HEAD and exit
with "nothing to do".

Fetch latest and compute the change set:

```bash
git fetch origin
CURRENT_SHA=$(git rev-parse HEAD)
```

If `LAST_SHA` equals `CURRENT_SHA`, update the state file and exit:

```bash
echo "$CURRENT_SHA" > website/docs/context/.last_scan_sha
git add website/docs/context/.last_scan_sha
git commit -m "doc-sync: update scan marker (no changes)"
```

Output: "No changes since last scan. Nothing to do."

Otherwise, examine what changed:

```bash
git log --oneline "$LAST_SHA".."$CURRENT_SHA"
git diff --name-only "$LAST_SHA".."$CURRENT_SHA"
```

### Step 2: Run Phase 1 — ADR Maintenance

See **Phase 1** section below. If Phase 1 produces changes, create a branch
and MR. If not, skip to Phase 2.

### Step 3: Run Phase 2 — Wiki Drift Repair

See **Phase 2** section below. If Phase 2 produces changes, create a branch
and MR. If not, skip to Phase 3.

### Step 4: Run Phase 3 — Traceability Audit

See **Phase 3** section below. If Phase 3 produces changes, create a branch
and MR.

### Step 5: Update State and Report

After all phases complete, update the scan marker:

```bash
git checkout master  # or whatever branch we started on
echo "$CURRENT_SHA" > website/docs/context/.last_scan_sha
git add website/docs/context/.last_scan_sha
git commit -m "doc-sync: advance scan marker to $(echo $CURRENT_SHA | head -c 8)"
git push origin HEAD
```

Print a summary report to stdout:

```
=== Doc-Sync Summary (YYYY-MM-DD) ===
Commits scanned: N (LAST_SHA..CURRENT_SHA)
Phase 1 (ADR Maintenance):  [N ADRs updated | no changes] [MR: !NNN | skipped]
Phase 2 (Wiki Drift):       [N pages fixed | no changes]  [MR: !NNN | skipped]
Phase 3 (Traceability):     [N gaps fixed | no changes]   [MR: !NNN | skipped]
```

## Branch and MR Creation (shared by all phases)

Each phase that produces changes follows this workflow:

```bash
PHASE_NAME="context"  # or "drift" or "traceability"
DATE=$(date +%Y-%m-%d)
BRANCH="doc-sync/${PHASE_NAME}-${DATE}"
```

**Idempotency check** — skip if branch already exists on remote:

```bash
if git ls-remote --heads origin "$BRANCH" | grep -q "$BRANCH"; then
  echo "Branch $BRANCH already exists on remote. Skipping phase."
  # Continue to next phase — do NOT abort
fi
```

**Create branch, commit, push, open MR:**

```bash
git checkout master
git checkout -b "$BRANCH"
# ... make changes ...
git add -A
git commit -m "doc-sync(${PHASE_NAME}): <summary of changes>"
git push -u origin "$BRANCH"
```

Open MR via glab (requires `dangerouslyDisableSandbox: true`):

```bash
glab mr create \
  --source-branch "$BRANCH" \
  --target-branch master \
  --title "doc-sync(${PHASE_NAME}): automated fixes $(date +%Y-%m-%d)" \
  --description "$(cat <<'MRDESC'
## <Phase title> (auto-generated by doc-sync)

### Changes
<bulleted list of changes>

### Metrics
<coverage/count metrics if applicable>
MRDESC
)" \
  --label doc-sync,"$PHASE_NAME" \
  --remove-source-branch
```

Return to master after MR creation:

```bash
git checkout master
```

## Error Handling

- **glab auth failure**: Abort immediately. Do NOT advance `.last_scan_sha`.
  Report the error.
- **Branch push failure (permissions)**: Abort the current phase, but continue
  to the next phase. Report the error for the failed phase.
- **All other errors** (unexpected wiki format, missing files, parse errors):
  Process best-effort. Do NOT skip. Do NOT abort. Fix what is fixable and
  continue to the next check/phase.

## Phase 1: ADR Maintenance

### What This Phase Does

Scan all existing ADR files in `website/docs/context/adr/` and verify they are accurate
against the current codebase. This phase does NOT create new ADRs — that is
`submit-gitlab-mr`'s job.

### Checks

For each `.md` file in `website/docs/context/adr/` (excluding README.md):

1. **Parse frontmatter** — extract `number`, `title`, `status`, `date`,
   `source_commits`, `superseded_by`.

2. **Dead references** — scan the ADR body for file paths (patterns like
   `src/...`, `tensorrt_model_connect/...`, `tests/...`, `include/...`). For each path,
   verify it exists in the repo. If a file was renamed or moved, use
   `git log --follow --diff-filter=R -- <old_path>` to find the new name.
   Update the reference inline.

3. **Dead symbol references** — scan for backtick-quoted identifiers (class
   names, function names, strategy strings). Grep the codebase to verify they
   still exist. If renamed, update.

4. **Stale factual claims** — look for numeric claims ("17 strategies",
   "54+ families", "68 models") and verify against current counts:
   - Strategy count: `grep -r "PluginRegistrar" src/runtime/plugins/ | grep -c "g_"`
   - Family count: `find tensorrt_model_connect/tensorrt_model_connect/families/ -name "*.py" -not -name "__init__.py" -not -name "base.py" | wc -l`
   - Model count: `find tests/e2e/models/ -name "*.json" | wc -l`
   Update claims to match reality.

5. **Status lifecycle** — if an ADR has `status: Proposed` and its `date` is
   more than 30 days ago:
   - Check if the decision is clearly implemented (the files/patterns it
     describes exist in the codebase).
   - If yes, change status to `Accepted`.

6. **Superseded decisions** — if an ADR describes a pattern that no longer
   exists in the codebase (e.g., "dispatch via switch/case" but code now uses
   registry), and a newer ADR describes the replacement:
   - Set `status: Superseded` and `superseded_by: <newer ADR number>`.
   - If no newer ADR exists, just update the content to reflect current state.

7. **Orphaned ADRs** — if `source_commits` are listed, check if those commits
   exist on the current master branch:
   ```bash
   git merge-base --is-ancestor <sha> HEAD
   ```
   If the commit is not an ancestor of HEAD (reverted or unmerged), mark the
   ADR as `Deprecated` with a note explaining why.

8. **Index drift** — after all checks, rebuild `website/docs/context/adr/README.md`:
   - Read all ADR files, extract frontmatter
   - Sort by number
   - Write the index table:
     ```markdown
     | Number | Title | Status | Date |
     |--------|-------|--------|------|
     | 0001 | <title> | Accepted | 2026-03-15 |
     | 0002 | <title> | Proposed | 2026-03-28 |
     ```

### MR Description Template

```markdown
## ADR Maintenance (auto-generated by doc-sync)

### Changes
- ADR 0003: updated file path `src/old.cpp` → `src/new.cpp`
- ADR 0005: promoted from Proposed → Accepted (implemented 35 days ago)
- ADR index: rebuilt (was missing ADR 0007)

### ADR Status Summary
- Total: N
- Accepted: N
- Proposed: N
- Deprecated: N
- Superseded: N
```

## Phase 2: Wiki Drift Repair

### What This Phase Does

Scan all markdown files in `website/docs/wiki/` and fix every factual claim to match
the current codebase. Auto-fix everything — the MR review is the human gate.

### Gathering Ground Truth

Before checking any wiki page, collect the following ground truth from the
codebase. Cache these values for reuse across all pages.

**Strategy registry (source of truth for strategy counts and tables):**

```bash
# Extract all registered strategy strings and their plugin files
grep -rn "PluginRegistrar" src/runtime/plugins/ --include="*.cpp"
```

Parse each line to extract: strategy string, plugin class name, source file.
Build a lookup table: `{strategy_string -> (plugin_class, plugin_file)}`.

**Family plugins (source of truth for family counts and lists):**

```bash
# Count family plugin files (excluding base.py and __init__.py)
find tensorrt_model_connect/tensorrt_model_connect/families/ -name "*.py" \
  -not -name "__init__.py" -not -name "base.py" | sort
```

For each file, extract the `plugin` attribute's `name` field by reading the
file and finding `name = "..."` or `name: str = "..."` on the plugin instance.

**E2E model manifests:**

```bash
find tests/e2e/models/ -name "*.json" | sort
```

Count and list all manifests. For each, extract `name` and `runtime_strategy`.

**Pipeline classes:**

```bash
find src/runtime/pipelines/ -name "*.h" | sort
```

**Test files:**

```bash
# Python builder tests
find tests/builder/ -name "test_*.py" | wc -l

# C++ runtime tests
find tests/cpp/ -name "test_*.cpp" | wc -l

# Tools self-tests
find tests/tools/ -name "test_*.py" | wc -l
```

**Source layout tree:**

```bash
# Generate actual directory tree for comparison
find src/ -type f \( -name "*.cpp" -o -name "*.h" \) | sort
find tensorrt_model_connect/tensorrt_model_connect/ -type f -name "*.py" | sort
find include/ -type f -name "*.h" | sort
```

### CRITICAL: Source Code Verification Rule

**Never rewrite a behavioral description based on grep output alone.** Before
changing any prose that describes how code works (dispatch flow, state
management, API contracts, etc.), you MUST:

1. Read the actual source file(s) being described (not just grep for symbols)
2. Understand the current behavior by reading the implementation
3. Rewrite the description to match what the code actually does

Counts and file paths can be fixed mechanically. Behavioral descriptions
require reading source code. This is non-negotiable.

### Per-Page Checks

For each wiki page, read the current content, then apply these checks:

#### Architecture-Overview.md

1. **Strategy count claims** — find all patterns like "N runtime strategies",
   "N registered", "N strategies". Replace N with the actual count from the
   strategy registry ground truth.

2. **Strategy tables** — find markdown tables that list strategy strings. Compare
   rows against the registry ground truth. Add missing rows, remove rows for
   deleted strategies, update plugin/pipeline class names.

3. **Family count claims** — find patterns like "N family plugins", "N+ families",
   "N+ Python files". Replace with actual count.

4. **Family lists** — if the page lists family names, verify each exists as a
   `.py` file in `families/`. Add missing, remove deleted.

5. **File path references** — every backtick-quoted path (e.g.,
   `` `src/runtime/registry/pipeline_factory.cpp` ``) must resolve to an
   existing file. Fix or remove dead paths.

6. **Class/function name references** — every backtick-quoted symbol must be
   findable via grep. Fix renamed symbols.

7. **Dispatch pattern description** — READ `src/runtime/registry/pipeline_factory.cpp`,
   `include/trtmc/runtime/pipeline_registry.h`, and
   `include/trtmc/runtime/pipeline_plugin.h` in full. Verify the wiki accurately
   describes the current dispatch mechanism. If it describes an obsolete pattern
   (e.g., enum-based dispatch, per-family factory functions), rewrite it based
   on what the actual source code does.

#### Source-Layout.md

1. **Directory tree** — compare the documented tree against the actual filesystem.
   Add new files/directories, remove deleted ones, update descriptions.

2. **File counts** — "N test executables", "N test modules", etc. Update to
   actual counts.

3. **Plugin file tables** — tables listing plugin files and their strategies.
   Sync with registry ground truth.

4. **Pipeline class tables** — tables listing pipeline implementations. Sync
   with actual files in `src/runtime/pipelines/`.

#### Testing-and-Validation.md

1. **Test layer tables** — tables listing test files, counts, GPU requirements.
   Update file counts and add/remove rows for new/deleted test files.

2. **Key files tables** — per-layer tables of test files with descriptions.
   Add missing test files, remove deleted ones.

3. **Test count claims** — "N tests", "N test modules", etc. Update to actual.

4. **E2E model count** — "N models", "N manifests". Update to actual.

5. **Manifest schema example** — verify the documented schema fields match
   what actual manifests use (read 2-3 manifests and check).

#### Traceability-Matrix.md

1. **File path references in UD-* entries** — every file path in UD-* rows
   must exist. Fix stale paths.

2. **Test file references in UT-* entries** — every test file path must exist.
   Fix or remove stale references.

3. **Strategy lists in ARCH-CFG-001** — the list of `runtime_strategy` values
   must match the current registry. Add new strategies, remove deleted ones.

4. **E2E manifest references in IT-* entries** — verify manifest files exist.

#### Static-Design.md

1. **Class names** — verify all documented class names exist via grep.
2. **Interface names** — verify `IPipeline`, `IPipelinePlugin`, etc. exist.
3. **Method signatures** — verify documented method names on classes.
4. **Class diagrams / relationships** — READ the header files for each documented
   class. Verify inheritance, composition, and method signatures match reality.

#### Pipeline-Deep-Dive.md

1. **Dispatch flow description** — READ `src/runtime/registry/pipeline_factory.cpp`
   in full. Verify every step of the documented dispatch logic matches the actual
   code. Rewrite if it has changed. Do not guess from function names.
2. **Legacy normalization** — READ the normalization code in pipeline_factory.cpp.
   Verify documented legacy strategy aliases match actual code.
3. **Per-pipeline sections** — for each pipeline described, READ the pipeline
   header/cpp to verify the description is accurate.

#### All Remaining Wiki Pages

For every other `.md` in `website/docs/wiki/`:

1. **File path references** — verify all backtick-quoted paths exist.
2. **Symbol references** — verify all backtick-quoted identifiers exist via grep.
3. **Numeric claims** — verify counts match reality.
4. **Behavioral descriptions** — READ the referenced source file(s) and verify
   the prose accurately describes current behavior. Rewrite if stale.
   Do not rewrite based on grep results alone.

### Post-Phase Verification

After making all changes but BEFORE committing, verify your work:

1. **Spot-check 3 behavioral rewrites** — for 3 wiki sections where you rewrote
   a behavioral description, re-read the source file and confirm your rewrite
   is accurate. If you find an error, fix it.

2. **Verify all file paths you added** — for every new file path you introduced
   in any wiki page, confirm it exists via Glob.

3. **Verify count consistency** — the same count (e.g., strategy count) must be
   identical everywhere it appears across all wiki pages. Search for the old
   count value across all modified pages to catch any you missed.

## Phase 3: Traceability Audit

### What This Phase Does

Scan the entire trace ID system and fix all gaps. This is purely mechanical.

### Scanning

**Step 1: Build the current matrix state.**

Read `website/docs/wiki/Traceability-Matrix.md` and extract all trace IDs:
- All `ARCH-*` IDs and their linked `UD-*`, `UT-*`, `IT-*` entries
- All file paths referenced by each entry

**Step 2: Scan test files for trace annotations.**

IMPORTANT: This codebase uses TWO trace annotation formats. Search for BOTH:

For Python tests in `tests/builder/`, `tests/tools/`:

```bash
# Search for both "Trace:" and "Trace ID:" formats
grep -rn "Trace:" tests/builder/ tests/tools/ --include="*.py"
```

For C++ tests in `tests/cpp/`:

```bash
# C++ tests use "Trace ID:" (multi-line ISO block) or "Trace:" (inline)
grep -rn "Trace" tests/cpp/ --include="*.cpp" | grep -E "Trace:|Trace ID:"
```

Parse each match to extract trace IDs (patterns: `ARCH-*`, `UD-*`, `UT-*`, `IT-*`).
A file is annotated if it contains EITHER `Trace:` or `Trace ID:`.

**Step 3: Scan E2E manifests.**

```bash
ls tests/e2e/models/*.json
```

Each manifest should have a corresponding `IT-E2E-<MODEL>-NN` entry.

**Step 4: Scan source files.**

```bash
find src/ -name "*.cpp" -o -name "*.h" | sort
find tensorrt_model_connect/tensorrt_model_connect/ -name "*.py" -not -name "__init__.py" | sort
```

Each source file should be referenced by a `UD-*` entry.

### Checks and Fixes

1. **Tests missing trace IDs** — search for BOTH `Trace:` and `Trace ID:` patterns
   (both formats are used in this codebase). For each test file that has neither:
   - Read at least 20 lines of the test to understand what it actually tests
   - Use the ARCH-* ID Assignment Guide above to pick the correct ID
   - Assign a new `UT-*` ID following the naming convention:
     `UT-<DOMAIN>-<LANG>-NN` (e.g., `UT-BDL-CPP-01`, `UT-CFG-PY-01`).
   - Add the trace annotation to the test file:
     - **Python**: add `Trace: <IDs>` line to the module or function docstring.
     - **C++**: add `// Trace: <IDs>` comment at the top of the file (after
       the copyright/header guard). Use the multi-line ISO 26262 block format
       if other test files in the same directory use it.
   - If the test also lacks Intent/Preconditions/Postconditions, add those
     based on reading the test code:
     - **Python format:**
       ```python
       """<existing docstring if any>

       Trace: ARCH-XXX-NNN, UD-XXX-NN, UT-XXX-LANG-NN
       Intent: <what behavior/contract is validated>
       Preconditions: <setup/assumptions>
       Postconditions: <observable outcomes guaranteed by assertions>
       """
       ```
     - **C++ format (match existing style in the file or directory):**
       ```cpp
       // Trace: ARCH-XXX-NNN, UD-XXX-NN, UT-XXX-LANG-NN
       // Intent: <what behavior/contract is validated>
       // Preconditions: <setup/assumptions>
       // Postconditions: <observable outcomes guaranteed by assertions>
       ```

2. **Orphaned trace IDs** — for each `UT-*`/`IT-*` in the matrix:
   - Verify the referenced test file exists.
   - If not, check if it was renamed via `git log --follow --diff-filter=R`.
   - If renamed, update the reference.
   - If truly deleted, remove the entry from the matrix.

3. **Unverified ARCH-* entries** — for each `ARCH-*` with zero linked `UT-*`
   or `IT-*`:
   - Search test files for tests that exercise the architecture contract
     (match by keywords from the contract description).
   - If matching tests found, link them.
   - If no tests exist, add a row with status `gap -- no verification evidence`.

4. **Missing UD-* coverage** — for each source file not referenced by any
   `UD-*` entry:
   - Determine the appropriate `ARCH-*` parent based on directory and purpose.
   - Assign a new `UD-*` ID following the convention.
   - Add a row to the appropriate matrix section.

5. **Stale UD-* references** — for each `UD-*` referencing a nonexistent file:
   - Check for rename via git log.
   - Fix or remove.

6. **Unlinked E2E manifests** — for each `.json` in `tests/e2e/models/` with
   no `IT-E2E-*` entry:
   - Create an `IT-E2E-<MODEL>-01` entry in the matrix.
   - The model name is derived from the manifest's `name` field (uppercase,
     hyphens to underscores): `qwen3-0.6b` -> `IT-E2E-QWEN3_0_6B-01`.

7. **Trace ID format violations** — scan all trace annotations for:
   - Wrong prefix (e.g., `TRACE-` instead of `UT-`)
   - Missing hyphen separators
   - Inconsistent casing
   Fix formatting inline.

### Matrix Expansion

After fixing existing entries and annotating test files, EXPAND the matrix:

1. **Add UD-* entries for uncovered source files** — compare the list of all
   source files (from Step 4) against files referenced in UD-* entries. For
   each source file with no UD-* entry:
   - Determine the appropriate matrix section based on directory
   - Assign a new UD-* ID
   - Add a row with the file path and a brief description (read the file header)

2. **Add UT-* entries for newly annotated tests** — for each test file where
   you added a trace annotation in Check 1, add a corresponding UT-* entry to
   the matrix linking it to the appropriate ARCH-* and UD-* entries.

3. **Add IT-E2E-* entries for unlinked manifests** — for each E2E manifest
   with no IT-* entry, add one.

4. **Update the matrix summary section** — recalculate coverage percentages
   after all additions.

### Post-Phase Verification

After making all changes but BEFORE committing:

1. **Verify ARCH-* ID accuracy** — randomly sample 5 test files you annotated.
   Read the test body (not just the filename). Confirm the ARCH-* ID you
   assigned actually matches what the test exercises. If wrong, fix it.

2. **Verify matrix consistency** — for 3 newly added UD-*/UT-* rows, verify
   the file path exists and the ARCH-* parent is correct.

3. **Count check** — verify the coverage metrics in the MR description match
   reality by running the scan commands from Steps 2-4 again.
